# 公司级 AI 智能体总控改造方案

状态为待评审设计稿。日期为 2026-11-19。

## 1. 业务目标与范围

本项目作为公司级、多成员、多项目接入的 AI 智能体最高执行总控，集中维护公司规约、技能、客户端适配和接入工具，形成可发布、可验证、可追溯、可回滚的执行基线。

主要用户包括平台维护者、安全负责人、技术栈负责人、业务仓库负责人及使用 Agent 的项目成员。平台维护者负责发布和适配，安全负责人负责权限边界与例外，技术栈负责人维护领域技能，业务仓库负责人维护项目上下文及升级。

首期覆盖现有 Codex 与 Antigravity 接入、规约分层、版本分发、诊断与回滚。客户端的最低支持版本在试点实测后填写。后续按实测能力扩展其他客户端。

设计基于多人使用各自工作副本、多个项目独立升级、开发机与 CI 使用相同规则版本的场景。实际项目数量、终端管理能力和试点项目由推广负责人确定。

## 2. 当前链路与主要问题

当前链路为初始化脚本 → 外部项目软链接 → 总控与技能 → 客户端执行 → 反馈文件与看板。工作台额外提供角色切换、Agent 调用及文档持久化。

| 位置 | 已确认现状 | 改造目标 |
| --- | --- | --- |
| `AGENTS.md`、`.gitignore` | 根入口链接到 `GEMINI.md`，被 Git 忽略 | 干净检出即可发现稳定入口 |
| `core-rules/INSTRUCTIONS.md` | 人设、规则加载、研发流程、提交交互和反馈归档集中在一起 | 短入口与按任务加载的规则分离 |
| `core-rules/INSTRUCTIONS.md` | 规定项目规则冲突时拥有最高优先级 | 明确强制基线、可覆盖默认项及项目扩展范围 |
| `automation-tools/init-project.sh` | 向本地源目录建立绝对软链接，更新跟随工作副本 | 项目固定完整发布版本，升级显式进行 |
| `automation-tools/init-project.sh` | 使用 `ln -sf` 写入入口，已有普通文件缺少归属判定 | 修改前识别归属，保存原内容并支持恢复 |
| 工作台 `server.js` | 角色激活改写共享 `GEMINI.md` | 角色状态随会话隔离 |
| MCP 配置挂载 | 使用本机 `.agents/mcp_config.json` | 按客户端和项目权限生成配置，凭据外置 |
| 全局反馈流程 | 引用个人路径，反馈可直接修改共享源 | 项目内脱敏收集，经回归和发布后推广 |

## 3. 规则分类与优先级

### 3.1 内容分类

| 类别 | 内容 | 存放位置 | 生效方式 |
| --- | --- | --- | --- |
| 公司强制控制 | 凭据权限、生产访问、写入范围、工具与网络访问限制 | 公司策略声明及适配器 | 托管配置、服务端身份权限、沙箱、CI 等执行点 |
| 公司默认规约 | 验证要求、变更范围、日志、反馈和研发约定 | `core-rules/` | 项目入口加载，明确允许覆盖的条目 |
| 技术栈标准 | Go、Java、React、Vue 的特有规则 | `stack-templates/` | 按实际改动匹配 |
| 任务技能 | 排障、代码审查、需求分析、架构分析等 | `stack-templates/skills/` | 任务符合触发条件时加载 |
| 项目上下文 | 业务目标、架构、目录边界、真实验证命令 | 业务项目自有文档 | 项目负责人维护并提交 |
| 用户与会话状态 | 当前角色、偏好、任务进度 | 用户本地或会话状态目录 | 按用户、项目、会话分别隔离 |

### 3.2 冲突处理

公司规则受客户端自身指令层级、系统权限和实际可用能力约束。公司需要强制执行的限制必须绑定实际执行点，文档声明记录其意图、范围和验证方式。

普通规则在公司默认、技术栈、项目和目录范围内逐层细化。每项可覆盖默认规则声明允许调整的字段。任务要求在授权范围内选择工作方式。项目声明触及强制基线时，诊断给出冲突并要求采用已批准的例外。

例外记录包含规则 ID、项目、环境、批准角色、理由、生效与到期时间、补偿措施。平台校验过期例外，实际权限由对应执行系统撤销。开发机时钟或本地文件不足以作为唯一的到期控制。

首期只给强制控制和可覆盖默认项分配稳定 ID，避免把全部叙述拆成结构化规则。元信息记录负责人、适用范围、验证命令、执行点和关联说明。Markdown 保留中文权威正文，元信息引用正文路径。

### 4.1 规范源仓库

```text

GEMINI.md                         兼容入口，复用同一份稳定正文
core-rules/

  policies.json                   首批控制元信息
  security-guardrails.md          安全规则权威正文
  agile-dev-lifecycle.md          按风险选择的研发流程
stack-templates/                  保留语言标准和技能原有路径
adapters/
  compatibility.md                客户端与版本实测矩阵
  codex/                         入口与配置模板、验证说明
  antigravity/                   入口与配置模板、验证说明
automation-tools/
  init-project.sh                 兼容已有调用的安装入口
  build-standards.js              构建发布目录与清单
  manage-standards.js             安装、升级、诊断、回滚的共享逻辑
  check-standards.js              源文件与产物静态校验
tests/standards/                  安装迁移及规则生效场景
docs/                             架构、接入、发布与迁移说明

```

共享安装逻辑使用现有 Node 运行环境和标准库。Shell 入口保留参数兼容及环境检测。若试点终端缺少 Node，将运行时依赖作为明确接入条件，评审后再决定是否提供额外发行方式。

根入口优先建议采用受 Git 跟踪的普通 `AGENTS.md`，`GEMINI.md` 作为仓库内相对链接。迁移前先更新工作台写入逻辑和初始化器，并验证 Git 及目标客户端的链接行为。需要普通文件的客户端通过生成与一致性校验保持正文一致。

### 4.2 接入业务项目

```text
AGENTS.md                         受管理入口块及项目自有规则
GEMINI.md                         客户端所需的兼容入口
.agents/
  standards.lock.json             项目固定的版本、摘要与选用能力
  standards/
    releases/<digest>/            安装后只读使用的完整版本目录
  state/                         本机事务、备份和诊断状态
  skills/                        公司技能与项目技能的可追踪组合
docs/ai/project-context.md        项目团队维护的业务与架构上下文
```

入口、锁文件、项目上下文及客户端所需的非敏感项目配置进入版本控制。发布缓存与本机状态按精确路径忽略。CI 根据锁文件获取并校验同一产物。离线场景可从预先下载的已验证产物安装。

技能目录逐项接入公司技能，保留项目自有技能。同名冲突要求显式选择，旧版 `.agents/skills` 整目录链接先验证并备份，再迁移为目录。生成入口使用直接指向版本目录的路径，切换提交完成前保留原版本。

## 5. 发布与项目版本契约

发布清单包含 schema 版本、发布版本、源提交、构建工具版本、文件列表、逐文件摘要、客户端适用范围和依赖运行时。项目锁文件包含版本、可信来源、产物摘要、选用技能、客户端、配置档与已批准例外引用。

发布使用语义化版本。改变覆盖规则、安装结构、强制控制或移除技能视为兼容性变化。新增兼容能力为次版本，修正文档及兼容修复为补丁版本。已发布版本禁止原地修改。

流程为变更分支 → 对应负责人评审 → 静态及回归检查 → 构建不可变产物 → 试点安装 → 发布稳定版本。业务项目通过升级变更提交更新入口和锁文件。

摘要用于校验传输与本机文件完整性。可信来源由受控仓库权限及发布身份提供，公司发布渠道具备签名能力后校验签名。下载包和清单来自同一未受信来源时，摘要不足以证明发布者身份。

初期使用 Git 托管的发布附件及项目锁文件即可分发。项目清单与升级情况从接入项目的 CI 报告汇总，后续依据实际接入规模决定是否增加在线服务。

## 6. 接入、升级和恢复

### 6.1 命令契约

下列为待实现接口。现有无参数调用保留，进入预检并输出接入计划。

```text
init-project.sh --version <version> --client <client> --dry-run
init-project.sh --version <version> --client <client> --apply
init-project.sh --update --version <version> --dry-run
node automation-tools/manage-standards.js doctor --project <path>
node automation-tools/manage-standards.js rollback --project <path> --transaction <id>
```

`--client` 支持明确选择多个已验证客户端，生产接入要求指定完整版本。旧 `-u`、`--update` 保留为升级入口，缺版本时显示可选版本及差异，通过正常交互选择。CI 使用明确参数并在缺项时失败。

### 6.2 安装事务

1. 获取项目级独占锁，记录事务 ID、目标版本、当前锁文件摘要及待修改文件摘要。并发安装返回可理解的状态。
2. 预检客户端与运行时、项目文件、链接真实目标和文件归属。对本机源链接、相对链接、普通文件、悬空链接分别建立迁移计划。
3. 下载或读取指定产物到暂存目录，校验可信来源与清单。校验归档路径，拒绝路径逃逸及意外外部链接。
4. 将完整版本安装到同文件系统的版本目录，生成候选入口、锁文件和配置。对已有普通文件保留项目正文，只更新带归属标记的管理块。无法确定内容归属时停止相关写入并输出冲突 diff。
5. 保存将被修改文件的内容、类型、权限与链接目标。重新比对预检摘要，检测用户在安装期间的并发编辑。
6. 用同目录临时文件重命名替换单个文件，逐步记录事务进度，最后提交锁文件并标记成功。多个文件替换期间要求暂停 Agent 会话。
7. 执行安装后校验。失败时按事务恢复原文件。恢复前再检查摘要，后续人工编辑进入冲突处理，保留双方内容。

单文件重命名提供原子替换，多文件事务依靠日志恢复。异常退出后，下次启动先识别未完成事务并完成恢复，再允许新操作。旧发布目录在成功验证和保留期内继续保留。

运行中的 Agent 可能已经读取旧指令，升级完成后诊断提醒新建会话，并通过新会话确认加载版本。

### 6.3 诊断输出

`doctor` 分别报告安装、加载和控制验证状态，支持可读文本及 JSON。报告包含项目版本、产物摘要、文件漂移、入口来源、技能冲突、客户端版本、强制控制执行点、验证结果与修复命令。

静态校验只能证明文件与配置存在。无法获得客户端加载证据时标记为待验证。强制控制按允许和拒绝场景实测，缺少执行点时标记为未落实，并给出具体缺口。

## 7. 客户端适配与权限

`adapters/compatibility.md` 每行记录客户端、精确版本、操作系统、执行环境、入口加载、技能发现、配置路径、权限与网络控制、审计能力、验证日期和证据路径。

Codex 适配依据其原生指令与托管配置机制，结合终端管理能力安装相应限制。Antigravity 首先实测现有 `GEMINI_GLOBAL.md` 和 `.agents` 路径的加载结果，按已验证能力生成配置。

首批控制建议选择凭据访问、生产写入和跨项目数据访问。每项明确到数据库账号、MCP 服务端权限、客户端沙箱或 CI 检查等执行点。CI 的验证范围标为提交与发布阶段，运行时限制由运行时系统负责。

MCP 配置按项目显式启用，记录服务来源、版本、能力范围和所需凭据引用。凭据由用户环境或公司凭据系统提供。安装器校验配置字段和权限意图，服务端身份决定最终授权。

## 8. 工作台与反馈改造

工作台的角色选择保存为用户、项目和会话标识下的状态。发送 Agent 请求时组合稳定项目规则和当前任务角色，并记录规则版本。并发会话分别维护角色和取消状态。

现有 `ACTIVE_ROLE` 内容迁移时保留备份，由用户当前会话采用原角色。项目中稳定的职责说明进入项目上下文。客户端独立启动时仍能读到团队规则。

当前工作台监听本机地址，首期继续按单用户本机工具定位。若后续部署多人共享服务，需要单独设计身份认证、项目授权、会话隔离和写入审计后再开放访问。

反馈在项目内先生成脱敏草稿，记录规则版本、客户端、任务类型、现象、预期与复现条件。用户明确上报后送入中央反馈池。负责人评估后选择修正规则、技能、工具或项目上下文，附回归场景并随发布交付。

安全基线变更由安全负责人评审，技术栈技能由领域负责人评审。业务日志与源码按公司数据要求处理。已共享的个人知识库路径迁到用户级配置。

## 10. 阶段、依赖与完成条件

| 阶段 | 交付内容 | 完成条件 | 依赖 |
| --- | --- | --- | --- |
| P0 规则与入口 | 公司定位、治理规则、稳定入口、角色状态解耦 | 干净检出加载规则；双会话无串扰；个人路径退出公司通用规则 | 入口与工作台变更一起验证 |
| P1 发布与迁移 | 发布清单、版本锁定、安装升级、诊断、回滚 | 两项目两环境同版摘要一致；中断恢复和用户编辑冲突通过 | P0 入口格式稳定 |
| P2 控制与试点 | 客户端适配、三类控制、能力矩阵、CI | 每类控制允许与拒绝场景通过；缺口有负责人及补偿措施 | 实际客户端与终端管理环境 |
| P3 推广与反馈 | 接入指南、版本汇总、反馈回归及发布流程 | 执行一次完整升级和回滚演练，反馈修复进入后续版本 | 试点负责人验收 |

工期由实施前的文件影响评估及试点条件估算。首期试点建议选择一个普通研发项目和一个需要受控数据访问的项目，保证技术栈与客户端差异可被观察。

## 11. 验证场景与验收指标

自动化回归覆盖空目录接入、已有指令文件保留、旧链接迁移、技能重名、包含空格路径、重复安装、并发安装、下载失败、摘要错误、替换中断、备份恢复、恢复时用户编辑、已移除技能清理和只读目录失败。失败应保留原可用版本并报告恢复状态。

行为验证使用小型固定任务集，覆盖需求分析、只读审查、常规修复、SRE 排障、越权访问和反馈记录。检查实际加载证据、工具操作与结果。记录客户端和模型版本，对行为波动保留人工判定。

首期验收要求每个试点项目能报告具体产物摘要，所有安装异常场景通过，三类首批强制控制均有通过的允许与拒绝验证，回滚后能在新会话确认旧版规则。接入耗时、回滚耗时、人工干预次数和任务成功率先采集基线，再制定推广目标。

审计默认记录项目标识、规则版本、客户端、控制 ID、执行结果及关联任务标识。保留期限和查看权限由公司现有数据制度确定。

## 12. 待环境核实的决策

- 公司客户端的实际版本、操作系统、授权类型和可集中管理的配置范围。
- 发布附件的可信分发渠道、身份校验方式与离线要求。
- 平台、安全、技术栈及试点项目负责人的具体归属。
- 数据访问控制、MCP 身份、审计保留及例外审批使用的现有公司系统。

这些事项在接入诊断和试点准备中核实。源规则整理、稳定入口、角色隔离和安装迁移实现可以先行推进，强制控制验证在对应环境具备后完成。

## 14. 已实现接口与设计差异

远端 CI 配置已加入，负责人账号尚未配置。公司客户端加载和强制控制的验证状态以 walkthrough 为准。
